# F1 층 1 저자 계정 점검 — 절차 고정(2026-11-24, 실행 전)

## 왜
- F1 재확인에서 Claude가 놓친 4편은 모두 같은 유형이었다. 논문에 링크가 없고 저장소는 저자 개인 GitHub 계정에만 있었다.
- 층 1의 나머지 `찾음` 아닌 40편은 저자 계정을 체계적으로 본 적이 없다. 그래서 4/44는 하한이다(`notes/lit/f1/f1_recheck_log.md` 최종 집계).
- 이 점검은 그 하한을 좁히려는 것이다. **탐색적 보충**이며 사전 등록 F1 재확인의 주 지표는 바꾸지 않는다. 결과는 별도 수치로 보고한다.

## 대상
`replication/f1_recheck.py`의 `strata()` 층 1(사전 등록 커밋 6cac6d6 기준 44편) 중 최종 시트 판정이 `찾음`이 아닌 40편.

## 절차(스크립트 `replication/f1_author_sweep.py`, 이 문서와 같은 커밋에 고정)
1. **저자 목록**은 다음 순서로 구한다.
   - arXiv 식별자가 있으면 arXiv API로 구한다.
   - 없으면 Semantic Scholar API로 DOI를 조회하고, DOI도 없으면 제목을 검색한다. 제목 검색은 `f1_candidates.csv`·시트의 제목을 쓰고, 첫 결과의 제목이 시트 제목의 핵심어를 포함할 때만 채택한다.
   - 확인 대상은 **1저자와 마지막 저자**다. 교신저자는 메타데이터로 알 수 없어 마지막 저자로 대신한다.
   - 저자를 못 구하면 "저자 확인 불가"로 적는다.
2. **계정 후보.** 저자마다 GitHub 사용자 검색(`fullname:"이름" type:user`)의 상위 3개 계정을 후보로 삼는다.
3. **저장소 후보.** 후보 계정이 직접 소유한 공개 저장소 중 포크가 아닌 것 전부(최대 100개)를 보고, 아래 중 하나라도 맞으면 후보로 삼는다.
   - 저장소 이름이나 설명에 논문 핵심어(방법 약어, 제목의 고유 단어)가 들어 있다.
   - 저장소 README에 arXiv 번호나 제목 일부(연속 4단어 이상)가 있다.
4. **arXiv 번호 README 검색.** arXiv 번호가 있으면 GitHub 저장소 검색(`"<번호>" in:readme`)도 한다. 결과 저장소 주인이 저자 이름과 같으면 후보로 삼는다.
5. **판정.** 스크립트는 후보만 낸다. Claude가 후보 README를 읽어 다음 기준을 적용하고, 결과는 **Claude 판독**으로 둔다.
   - `찾음` 기준(`notes/lit/f1/f1_judging_guide.md` 4단계): 저자 계정이고 README나 저장소가 이 논문을 가리킨다.
   - 사람 확인 목록을 만들어 사용자가 확인한 것만 "사람 확인"으로 바꾼다.

## 보고(고정)
- 점검 대상 수, 저자 확인 불가 수, 후보 수, Claude 판독 `찾음` 수, 사람 확인 `찾음` 수.
- `찾음`이 나오면 층 1 보충 수치를 함께 적는다: (4 + 사람 확인 찾음)/44, Wilson 95%.
  - 사전 등록 주 지표(4/44)는 그대로 두고, "저자 계정 점검 포함" 수치를 병기한다.
- 한계: 이름 동명이인, 이름을 다르게 쓴 계정(로마자 표기), 조직 계정은 이 절차로 잡히지 않는다. 그러므로 이 점검 뒤 수치도 하한이다.
- 이 절차를 결과를 본 뒤 바꾸지 않는다. 바꾸면 이탈로 적는다.

## 실행 기록
- **1차 실행**(2026-11-24, eed372f 스크립트): 40편 중 후보 있음 1편(P24-07), 후보 없음 27편, 저자 확인 불가 12편.
- **실행 오류 정정**(절차 문구는 바꾸지 않고 구현 오류만 고침. 판정 결과를 보기 전이며, 후보 1편의 README는 아직 열지 않음):
  1. arXiv 번호 추출이 DOI 안의 숫자를 잡았다(예 `j.eswa.2020.113573`→`2020.11357`). 대상은 alphastock, park2020dqn, W21_Benhamou_crisis, W22_MetaTrader, W21_DeepPocket, P24-03 6편이다. 이 편들은 저자 조회와 arXiv README 검색이 잘못된 번호로 돌았다. `arXiv` 표기가 붙은 번호만 잡도록 고쳤다.
  2. 실행 후반에 arXiv API 응답이 실패했다. 그래서 arXiv 번호가 있는 7편이 저자 확인 불가가 되었다(Y25-07, Y26-02, Y25-10, P23-03, yu2019modelbased 등). 호출 간격을 4초로 늘리고 재시도하며, 실패하면 Semantic Scholar `ARXIV:` 조회로 대신하도록 고쳤다.
  3. SUP-CLRS의 제목 검색("CLRS")이 이름만 같은 DeepMind CLRS 논문과 짝지어졌다. 1절 제목 검색 규칙의 핵심어 조건은 충족했지만 다른 논문이다. 저자 확인 불가로 처리한다(정정).
  4. GitHub 호출 실패를 조용히 빈 결과로 넘기던 부분을 고쳤다. 이제 재시도하고, 실패하면 `gh_errors`에 남긴다.
- 위 대상과 계정 0개였던 편(P24-09, Y25-09)을 다시 돌린다(`--redo=`).
- **양성 대조(판정과 무관, 도구 점검):** 저자 계정에서 이미 찾은 6편에 같은 절차를 돌려 몇 편을 잡는지 본다(`--control`, 출력 `f1_author_sweep_control.json`). 대상은 W22_PretoriusVanZyl, jiang2017crypto, Y26-01, Y26-03, Y25-03, SUP-LSRE다. 잡는 비율이 낮으면 "후보 없음"의 의미가 약하다는 뜻이고, 그 비율을 함께 보고한다.
