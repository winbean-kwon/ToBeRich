### MASA 상세
- 비용은 새 가중치를 정하는 시점에 자본에서 뗀다(`utils/tradeEnv.py` 203행). 기록 방식은 다음과 같다.
  - 그 비용을 **직전 시점의 수익 칸에 소급해** 적는다(204–205행 `asset_lst[-1]`, `profit_lst[-1]` 수정).
  - 당일 수익 `poDayReturn_withcost`(249행)는 비용을 뗀 뒤의 자본을 분모로 계산되므로 이름과 달리 비용이 빠진다.
- RL 보상은 이 당일 수익으로 계산된다(303행 `profit_part = log(1 + poDayReturn_withcost)`, 354행 `self.reward`). 같은 행동열에서 c = 0과 c = 0.0003의 보상열은 최대 절대 차이가 1e−12 이하였다(하네스 기준). 가치열은 매 스텝 달랐다. 학습 루프는 `env.step`의 보상을 그대로 replay buffer에 넣는다(`RL_controller/TD3_controller.py` 499·513행).
- 따라서 **학습 보상은 거래비용 차감 전 수익으로 계산되고, 비용은 자산 곡선(평가)에만 반영된다.** 사전 정의상 C1 "부분 부과(가치만)"이다. 이것이 의도된 설계인지는 코드로 판정하지 않는다. 이 문서는 이를 "버그"가 아니라 "보상–가치 불일치"로 부른다.
  - 제어기·주 설정(`js_loss`) 분기도 같은 `profit_part`를 쓴다(304–327행). 이 부분은 정적 판정이다. 동적으로 실행한 것은 제어기를 끈 else 분기다.
  - 종료 스텝(162–180행)은 직전 `self.reward`를 다시 반환하고, 청산 비용도 보상에 넣지 않는다.
  - 최적 모델 선택 기준 `reward_sum`도 비용을 포함하지 않는다(654–656행).
  - 비용이 닿는 곳은 관측의 log 자본(252행)과 자산 곡선 기반 지표뿐이다.

## 4. 해석 (탐색적, 판정 아님)
- 사전 예측대로, 감사한 신규 구현에서 비용 결함과 유한 비 상한은 반복되지 않았다. 확인된 사례는 이번 범위에서 FinRL SPE 계보에 모여 있다(EarnMore와 AlphaMix+의 tanh 출력은 예외).
  - 비용을 실제로 쓰지 않는 사례는 FinRL SPE 계보와 EarnMore에 있다.
  - 유한 비 상한은 FinRL SPE와 AlphaMix+(tanh 출력)에 있다.
  - EIIE/PGPortfolio 계열과 독립 구현 2개(DeepTrader, WaveCorr)는 둘 다 정상이었다.
- MASA는 FinRL SPE에서 파생됐지만 비용을 구현했다. 다만 보상 쪽에서 빠졌다. 결함의 형태가 "미부과"가 아니라 "보상–가치 불일치"(v2의 C2 유형)다.
- 논문에서 쓸 수 있는 문장은 "감사한 신규 공개 구현 5개(4개 계보) 중 1개(FinRL 파생)에서 학습 보상이 설정된 거래비용을 반영하지 않았고, 평가 자산 곡선에는 반영되었다. 매개화가 가중치 비를 유한하게 묶는 구현은 없었다"이다. 재현 3편의 성질은 특정 코드 계보에 국한된 것으로 서술한다.

## 5. 이탈과 수정 (결과 후)
1. **S1 시점 판정 로직 수정.**
   - 1차 실행에서 DeepTrader 주 설정이 "1스텝 지연"으로 나왔다. 원인은 비율이 1이 아닐 때(0.5) L1 오차 비교가 시차를 잘못 고르는 하네스 결함이었다. 코드상 비용은 같은 스텝에 부과된다(`portfolio_env.py` 294–295행).
   - 크기를 맞춘 뒤 상대 잔차를 비교하도록 고쳤고, 대조군 3개를 다시 통과시켰다. 1차 값은 `results_new_run1.json`에 남아 있다.
   - 1차 비율 0.517도 관례 차이 구간(0.5±0.02) 안이었다. "1스텝 지연"은 결함 정의에 들어가지 않으므로 판정은 바뀌지 않는다.
   - 대조군 재실행 결과는 커밋된 `controls_result.json`과 같았다.
2. **MASA 어댑터 보상 변수 변경.** 1차 실행은 보상으로 `profit_lst[-1]`를, 2차는 실제 RL 보상 변수 `self.reward`를 읽었다. 두 실행 모두 C1은 "부분 부과(가치만)"였다.
3. **RAT dtype.** 원 코드처럼 float32로 맞췄다. 1차 실행은 dtype 오류로 결과가 없었다.
4. **실행 방식.**
   - 저장소 모듈은 import하지 않았다. 읽은 클래스·함수 정의만 AST로 꺼내 실행했다.
   - MASA는 `Config()` 대신 env가 읽는 속성만 기본값으로 뒀다. 시장 관측기와 제어기는 껐다(학습 모델과 외부 데이터가 필요하다). 그 결과 `mode='RLonly'`와 `js_loss`가 함께 설정됐는데, 원본 `Config`는 이 조합을 허용하지 않는다(87–89행). 실행된 보상 분기는 else이고, 비용 처리 행은 같다.
   - RAT은 `.cuda()`를 CPU 항등으로 바꿨다.
   - 사전 등록 4장의 "모듈만 import"와 다르지만 더 보수적인 방식이다.
5. **P2(초기 출발점, 보조)는 측정하지 않았다.** 신규 대상 모두 R 무한이라 1/N 근접 주장의 근거로 쓸 일이 없다. 그래서 시간을 쓰지 않았다. 사전 등록이 허용한 "설치 실패로 미측정"과는 다른 이유이므로 이탈로 적는다.

## 6. 한계
- 신규 대상이 5개 구현, 4개 계보뿐이다. 공개 코드 표본이다.
- 합성 가격과 스크립트 행동을 썼다. 학습된 정책의 실제 회전율에서 나는 영향은 재지 않았다.
- MASA 보상에서 비용이 빠진 것이 학습된 정책이나 논문 수치에 어떤 영향을 줬는지는 재학습 없이 알 수 없다.
- 1인 감사다.
- DeepTrader는 롱 비율 p = 1로 실행했으므로 공매도 쪽 비용(299·311행)은 동적으로 점검하지 않았다.
- C1의 "보상"을 실제 RL 보상 변수로 읽은 것은 MASA뿐이다. 나머지는 평가 경로 값을 썼다.
  - 나머지 대상의 학습 보상에도 비용이 들어간다는 것은 정적 판정이다. RAT `Batch_Loss` 1017행, WaveCorr TF 그래프 `μ = 1 − fee·Σ|Δ|`(일부 분기는 드리프트 가중치가 아니라 `wIn`과 비교: 120·225·280·313행), DeepTrader `agent.py` 126행 `rewards.total`이다.
  - 이들은 학습 시 비용 형태(선형 근사)가 평가 시(반복 해)와 다르다.
- #5를 포함해도 판정은 같다. 그 저장소는 FinRL SPE를 import하므로 MASA와 같은 계보가 되고, 계보 수는 1로 유지된다.
